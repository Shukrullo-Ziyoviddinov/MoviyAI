# Catalogue preparation, saving and chat integration — steps 2–7

This module prepares/validates data, performs read-only duplicate checks and
resolves genres/countries/categories and saves verified film identities with available facts to R2 and
MongoDB. Supported chat movie results automatically start a durable background
job. Translation/research never runs in the chat response's critical path.

Flow: `MovieSearchResult` → `prepareCatalogDraft` → enrichment/reference/media/actor
stages → `assessCatalogDraft`. An invalid/unsupported draft has `payload: null` and precise
field/action issues. A draft is never itself a Movie insert payload.

## Field ownership and completeness

| Fields | Rule / responsible later stage |
| --- | --- |
| Movie `id`, actor `id` | Server allocates only after duplicate check; never generated by AI. Not part of create payload schemas. |
| Original title, release year, external IDs | Identity envelope. IMDb/Kinopoisk IDs come only from corresponding official film URLs; conflicting IDs remain unknown. Release year is not production period. |
| `categoryName` | One of the eight active categories, or null if unresolved. No arbitrary AI section names. |
| `title.uz`, `title.ru` | Nullable. Keep sourced names/translations; original identity title remains in catalogIdentity.originalTitle. UI may display that original name without changing stored locale fields. |
| `homeImgPoster` | R2-backed `/img/filename` after upload, or null when unavailable. External poster URLs remain candidates. |
| `ratingImdb`, `ratingKinopoisk` | Verified numbers 0–10 or null, never a fabricated zero. |
| `genre.uz`, `genre.ru`, `filterGenre` | Resolved dictionary arrays, possibly empty. Both locale arrays align; filters are a subset of Uzbek genre names. |
| `description.uz/ru.text`, `.country`, `.director` | Nullable. Use only sourced facts/translations and current dictionary labels. |
| `description.uz/ru.year`, `.duration` | Nullable and identical to specs counterparts. A known runtime is positive integer minutes. |
| `trailers` | The actual YouTube **trailer** watch URL, not a general related video. Canonical `https://www.youtube.com/watch?v=ID`. |
| `watchUrl` | First verified exact movie detail page from the four configured Uzbek sites. Never a media-file or homepage URL. All alternative choices remain in research. |
| `filterCountry`, `specs.countries` | Dictionary values. Primary country must be one of the production countries. Never map an unknown country to USA/India by default. |
| `specs.ageRating` | Source classification or null. Never convert MPAA to a guessed numeric age. |
| `like`, `dislike` | Server-controlled string `"0"` for a newly created film, not imported search-site reactions. |
| `franchiseMovieIds` | Existing internal movie IDs only. Empty is valid if no verified existing relation is found. Relation lookup remains a later stage. |
| `actorIds` | Unique positive integer IDs linked to verified actors. May be empty: unresolved cast is deferred independently instead of blocking the film. Never reuse movie cast position as actor ID. |
| Actor `actorName`, `actorImg`, `actorAbout.uz/ru` | Required for a new actor. Image must be stored in R2; biographies must be researched/translated. An existing resolved actor needs only its existing ID and is not recreated. |

Research attempts web evidence beyond IMDb/Kinopoisk for general movie facts.
Unavailable facts, posters or links are stored as null; unknown lists are empty.
Provider failures during optional enrichment do not prevent saving a supported
film identity. Original sources and missing field paths remain in private research
metadata. Invalid identities, conflicting versions, lost checkpoints and DB write
failures still stop/retry safely. Unknown-year films require a verified external
ID or dedicated named film page; source hashes prevent duplicate unknown-year rows.
Legacy empty link strings remain accepted, but new unknown links use null.

`research` preserves the complete sourced lookup result: production period,
budget, box office, writers, premiere, characters, age system/country, source
URLs, checkedAt, all posters and alternative Uzbek links. These are not inserted
as unsupported top-level Movie fields. The save service persists the full
envelope in `catalogResearch.result` (excluded from normal public queries).
Missing optional research facts remain explicit issues, not invented values.

Admin create/update APIs preserve their routes and support nullable Movie fields. Unknown
payload keys and AI-supplied numeric IDs are rejected by the strict schemas.
Dictionary membership is rechecked in the save transaction. New catalogue image
paths are assigned only after upload. Server counters allocate numeric IDs.

Admin form parsing also preserves blank numbers as null (an explicit zero rating
remains zero). Existing original identities can be edited without inventing locale
names or requiring missing optional descriptions/specs; a new unnamed record is
still rejected. Year/runtime replicas are synchronized and conflicting supplied
values are rejected. Poster uploads are optional for admin creation as well.

## Step 3: read-only identity matching

`repositories/catalog-match.repository.ts` reads bounded candidates from existing
`movies`/`actors`. `services/catalog-match.service.ts` decides without mutation:

- `existing`: confirmed catalogue ID may be reused.
- `not-found`: no matching candidate; continue enrichment/creation stages.
- `needs-research`: missing/ambiguous identity, incomplete legacy record, or
  bounded candidate limit reached. Never create or silently merge in this state.
- `conflict`: providers, release year or birth date contradict each other.

Movie matching prioritizes supported IMDb `tt…` / Kinopoisk film IDs. Otherwise
it compares exact normalized original/localized aliases **and release year**;
multiple candidates or contradictory director names require research. No fuzzy
title matching, script conversion, subtitle stripping or sequel-number guessing.

`MovieSearchResult.identitySources` isolates the verified film-identification and
film-rating pages from general display `sources`. Character/poster image pages
can refer to another adaptation and must not create conflicting film IDs in the
save pipeline. The outbox and enrichment preserve this boundary. Old snapshots
without identitySources still use their original sources conservatively; real
conflicting film IDs are never silently ignored.

Actor matching accepts an official IMDb `nm…` / Kinopoisk person ID, a sourced
full birth date plus exact normalized name, or a verified public actor profile
with two independent named film-role sources. A unique legacy name can be
reused when its stored biography matches that same verified film and role.
Namesakes, conflicting identities and name-only matches remain unresolved.
Accepted legacy identities are enriched under the same write transaction.
A legacy namesake without identity metadata blocks creation/reuse until research
can distinguish it. A valid external ID with a changed display name still matches.

`inspectCatalogDuplicates` accepts the preparation draft. Existing movies stop
the process before actor work. For new movies, only confirmed existing actor IDs
are copied into a **cloned** draft. New/uncertain actors have no invented IDs.
Repository errors propagate; DB failure never becomes “not found”.

Movie/Actor models now accept optional `catalogIdentity` metadata, with normalized
name keys and partial unique provider-ID indexes. Old rows need no migration to
remain readable. Future insert services must explicitly use `movieIdentityForInsert`
or `actorIdentityForInsert`; AI cannot inject these through current admin payloads.
No existing DB rows are backfilled here, and tests do not connect to the live DB.
Schema index declarations are not proof that deployment has built those indexes:
the insertion stage must ensure they exist and handle duplicate-key races.

Legacy rows missing normalized keys are included in candidate reads (same year
for movies); a cap of 100 prevents unbounded scans. Reaching the cap blocks the
decision until an explicit identity/backfill stage is performed. No broad name-only
unique index is used because different people/films can share names.

## Step 4: canonical catalogue references

`catalog-reference.repository.ts` reads only the current MongoDB `genres` and
`countries` collections. It never falls back to seed JSON on connection failure.
The eight active UI sections are centrally declared in
`config/catalog-reference.config.ts`; there is no category collection in this app.

`catalogReferenceResolver.resolve(draft)` returns a cloned draft and a readiness
report. Uzbek, Russian, English and common ISO country/genre aliases are explicit
configuration. An alias is **only** a matching hint, never an output value: the
exact `Genre.name`, paired `Genre.nameRu`, and `Country.name` come from DB rows.
Existing spelling such as `Dramma` is preserved. Custom dictionary values can match
directly; new aliases can be added without changing the service.

All sourced production countries are retained in first-occurrence source order;
the first resolved country supplies the single-valued `filterCountry`. This is a
deterministic filter policy, not an inferred claim about primary financing. Every
matched genre supplies the paired UZ/RU arrays and `filterGenre`. Duplicate aliases
collapse to one dictionary value. Description country fields use the same
canonical DB labels as country filters and specs.

Section precedence is explicit: animation, horror, science fiction, action,
romance, comedy, family, drama. Explicit additional genre rules and verified
dynamic genre categories route into these eight sections. A fantasy genre keeps
its own label even when routed into sciFiMovies; USSR/Russia and North/South Korea
remain distinct.

The pure resolver never writes data. Before pausing for missing rows, the chat
processor calls `catalog-dictionary.service.ts`: existing synonyms are reused;
new genres require a verified Gemini proposal, literal supporting search evidence
on two source domains and exact-movie evidence, canonical UZ/RU labels and an
existing UI category. Countries must map to the bundled country/territory/historical
reference; known absent entries do not need AI. New spellings are stored as aliases
so future requests use the current DB value without new search. Ambiguous or
unsupported proposals remain blocked, never substituted or silently dropped.
The dictionary repository uses the shared MongoDB transaction gate, a fresh
snapshot and unique normalized multikey indexes to prevent concurrent duplicates.
Source evidence for new rows is private. Old/stale reference fields are cleared in the returned draft
on failure so a partially resolved film cannot pass as complete. Issues identify
the original requested value and exact research field requiring attention.

The caller must require `result.ready` before continuing. A later save stage can
use `validateCatalogReferenceValues` with a **fresh** repository snapshot to reject
removed rows, changed translations, invalid section choices or altered filters.
Dictionary reads and resolution do not change MongoDB/R2 or invoke additional AI.

## Saving an enriched draft

Entry point: `saveCatalogMovie(draft)` in `services/catalog-save.service.ts`.
It returns `existing`, `created`, or `needs-enrichment`; infrastructure failures
throw so a future background job can retry. Existing movies are returned before
any upload or new actor work. The input is cloned, not mutated.

New actors require supported person identity, both researched biographies and
`imageCandidates` supplied by enrichment. Existing actor IDs are re-resolved from
DB, not trusted from input. The save service itself does not fabricate biographies,
translate fields, or identify a portrait's subject. A missing enrichment
field blocks saving before media transfer. A successful new actor insert is part
of the same transaction as the movie; there is no orphan actor on movie failure.

Poster candidates (up to two stored) and new actor portraits are downloaded
sequentially, max 4 MiB per image, with timeouts, content-signature checking and
HTTPS-only redirects. DNS answers are checked/pinned on the actual HTTPS socket;
internal/private/metadata destinations are rejected. No image scripts are run.
Bytes pass through the server once to upload to R2; this differs from direct R2
chat uploads. Random per-attempt filenames never overwrite shared assets. Stored
paths follow existing `/img/name` catalogue conventions. `catalogPosters` contains
the saved poster paths, `homeImgPoster` is the first one, and private
`catalogMediaKeys`/`catalogResearch` retain ownership and evidence.

Franchise relations require `franchiseCandidates`: each has an exact film
identity and a sourced relationship claim. Existing matching films are linked in
both directions; missing catalogue members are not created. Raw guessed numeric
IDs or a common title prefix never establish a relationship. No relationship is
inferred if enrichment supplied no evidence. Empty verified relations are valid.

`catalog-transaction.service.ts` requires MongoDB transactions (replica set/Atlas
or sharded deployment), initializes declared indexes without dropping any, and
uses a single durable `catalogCounters/write-gate` write in every transaction.
Concurrent API instances serialize/retry at that write and then recheck film and
actor identities using a fresh snapshot. Counter increments, new actors, movie,
and reciprocal franchise updates commit or roll back together. No downloads or
R2 calls occur in the retryable transaction callback. External-ID unique indexes
remain a second line of defence. Admin create/delete and dictionary rename/delete
paths share the gate; numeric allocation also accounts for current max legacy ID.
Offline seeds/import scripts must not run concurrently with catalogue writers.

Uploads happen before DB transactions. After success/failure or a losing
duplicate race, cleanup reacquires the same gate, determines which attempt-owned
keys are truly unreferenced, then deletes only those. An uncertain commit must not
delete media referenced by a committed record. If DB outcome or R2 cleanup is
unavailable, cleanup logs a deferred warning and preserves files. A process crash
between upload and DB write can leave unreferenced R2 objects; periodic orphan
reconciliation is not implemented here. Existing catalogue/user-upload assets are
never adopted or deleted by this upload attempt.

Tests use isolated fake repositories/transactions/R2, not the production DB. They
cover parallel saver instances, shared actors, rollback, changed dictionaries,
franchise links, unknown commit results, ID counters and image network boundaries.
Index and transaction behaviour still require deployment against transaction-
capable MongoDB. The configured DB topology was checked read-only; no production
catalogue/actor records or R2 files were created as test fixtures.

## Step 7: durable chat outbox and background worker

The completed `ai_chat_turns` update stores the answer, movie, portraits and
`catalogDispatch: pending` together. Eligibility requires a supported title and
public source, medium/high confidence, and a full movie result. Greetings,
unsupported guesses, and `linksOnly` follow-ups are not catalogue inserts. No
user confirmation is required. Dispatch/worker errors do not change chat status,
remove an answer, or trigger a second model response.

`catalog-dispatch.service.ts` copies only public movie facts and actor portrait
candidates into `ai_catalog_save_jobs`. The stable SHA-256 job key derives from
conversation/request IDs; an upsert never resets an existing job. Only after this
durable write does it acknowledge the outbox. A crash between those two writes
is safe to replay. User question text, original frame/video bytes and signed
user-upload URLs are not copied to jobs. Chat cleanup flushes remaining outbox
rows before deleting turns, so public catalogue work survives chat deletion.

`catalog-worker.service.ts` starts from server bootstrap, polls every 15 seconds,
and wakes on completed movie results. Each process runs one job at a time;
multi-instance claims are atomic DB updates with tokens and ten-minute leases.
A 30-second heartbeat renews ownership; status/checkpoint writes are token-fenced.
An expired processing lease is recoverable after a restart. Already durable jobs
still run if new outbox dispatch temporarily fails.

The processor first checks the existing catalogue (no paid research for an
existing movie). It checks actual genre/country dictionaries before expensive
enrichment. Missing verified facts use bounded Serper results and structured
source-index extraction. Derived UZ/RU display titles and description translations
retain the underlying sources; they are not claims of official dubbed titles.
Actor research prefers official person pages but also accepts public actor/studio
biographies and film-role evidence from other sources. IMDb is not mandatory.
Unsourced biographies and guessed person IDs are never filled. Per-actor provider
errors defer that actor without failing the completed film research.
Existing legacy namesakes without enough identity metadata remain blocked; this
worker does not automatically overwrite their identities. Only actor portraits
are reused, not character pictures. Missing posters can be searched again.

Franchise research accepts only series evidence that identifies the current film,
and explicitly cited member titles/years. The save service links only existing
catalogue members. Related YouTube clips are never saved as actual trailers.
Missing optional links are confirmed empty only after successful provider
searches; provider failures do not become invented URLs or availability claims.

Enrichment checkpoints are saved after movie facts, translations, each actor,
franchise research and link research, before storage. A storage retry can reuse
this work without regenerating the user's chat answer. Save still performs all
duplicate/reference checks and transaction locking from the previous stages.

Job states: `pending`, `processing`, `retry`, `needs-enrichment`, `failed`,
`completed`. Provider/storage errors back off from 30 seconds exponentially, with
at most five automatic attempts. Missing verified facts or unresolved dictionary proposals pause for
six hours between checks (also subject to the attempt cap). Exact blocking fields
are stored privately in `issues`; success records `movieId`. Internal maintenance
hook `retryCatalogJob(id)` can requeue a blocked/failed job; no unauthenticated HTTP
endpoint exposes it. `[AI_CATALOG]` logs contain statuses/field paths and numeric
provider status, not API keys, prompts or private chat media. A free server may
sleep; the queue resumes when the process is running again, rather than relying
on an in-memory promise to survive shutdown.

Chat response shape is unchanged. Catalogue scalar fields are nullable, and web,
native and admin readers handle missing values without fabricated zero ratings. Schema/index
definitions and worker startup ship with the server deployment. Tests cover
outbox replay, job fencing, restart/backoff, checkpoints, enrichment provenance,
conversation deletion and chat-answer independence using isolated dependencies.
# Catalogue-first image replies

## Independent cast completion

Actor uncertainty, missing biographies/photos and per-actor provider failures no
longer block movie insertion. A supported movie identity is still required;
missing optional facts/posters use null. The saver stages only verified actors and inserts the film
with their IDs, including `actorIds: []` if none can be resolved safely.

Unresolved cast is preserved privately in `catalogResearch.pendingActors` and
atomically queued in `ai_actor_enrichment_jobs` with the movie insert. This is
independent of the completed movie-save job. The first backfill is due after 15
minutes, later attempts after one hour; at most five attempts then status `paused`
retains the draft for review. Jobs use expiring leases and fenced checkpoints.
The worker resumes stored actor research, uploads only actor assets, rechecks
identities under the shared transaction gate and `$addToSet`s IDs to the existing
movie. It does not recreate deleted movies. Unreferenced staged assets are cleaned
using the same uncertain-commit-safe ownership checks as movie saves.
It skips unrelated movie rating, translation and poster research when a pending
cast list already exists, so unknown movie facts cannot delay actor completion.

Movie recommendations research up to three distinct films per reply. Each verified
result keeps its own dossier, media and portraits in the chat turn's `recommendations`
array. The outbox gives each result a stable per-index job key and only acknowledges
the turn after every eligible result is durably enqueued. Normal catalogue identity
checks still deduplicate films already in the database. Web and native reopen these
results as independent movie messages rather than combining their source/media blocks.

Actor enrichment searches biography, official person profile and exact film
credits separately. If profile/credit evidence is missing, it performs bounded
Kinopoisk-person/IMDb-film searches before generating sourced biographies.
The official profile heading must match the actor name (a namesake's snippet
mention is insufficient). Credit matching preserves sequel/version identity,
accepting punctuation and explicit part numeral variants only. Unrelated
official person IDs are excluded from the selected actor's identity sources.

Diagnostics: `[AI_CATALOG]` job events include `jobId`. Failed operations
include `provider`, `stage`, `providerStatus`, safe `errorKind`, and `model`
for structured Google enrichment calls. For example `google / actor-facts /
503` identifies actor extraction separately from `serper / actor-evidence`.
Raw SDK errors, URLs, query text, headers and private chat data are excluded.
The job's private issue message keeps the same safe operation labels. This
adds diagnosis only; it does not change retry limits or switch models.

Country maintenance: `npm run countries:sync` previews and
`npm run countries:sync -- --apply` adds missing reviewed countries without
renaming existing rows. `data/country.json` contains 250 country/territory
entries and five historical movie production states. Multilingual aliases
are bundled locally; see `data/COUNTRIES-SOURCE.md` for source and license.
Ambiguous Korea/Congo remain unresolved rather than choosing a country.

Genre dictionary maintenance: after building, run `npm run genres:sync` for a
preview or `npm run genres:sync -- --apply` to add reviewed missing rows from
`server/data/genre.json`. This does not seed movies/actors, overwrite existing
labels, or run automatically from chat. Conflicting concept aliases abort the
maintenance command. All 26 listed genres have explicit routing into the eight
existing UI categories; genres retain their own canonical UZ/RU labels.

Image recognition extracts tentative title aliases/year, then reads catalogue
candidates before Serper. Exact normalized names/year form the shortlist;
Gemini must confidently verify the frame against that shortlist. A verified hit
uses current Movie fields, stored research extras, catalogue poster paths and
Actor rows referenced by actorIds. No poster/portrait web search or save job is
scheduled for that hit. Missing legacy research fields remain unavailable.
If visual identity is uncertain or absent, normal web discovery continues. The
web-verified title is checked again before dossier/media research. New results
retain the durable background save flow; mandatory fact/reference failures can
still defer persistence. Catalogue media URLs use PUBLIC_URL and the existing
public media route, so PUBLIC_URL must identify this API deployment.
